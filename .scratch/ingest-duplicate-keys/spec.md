# Spec: Ingest de-duplication and landing file cleanup

**Status:** done (2026-10-11)
Category: bug
Raised: 2026-10-10 (as issue); promoted to spec 2026-10-11

> *Generated by AI from a working session on 2026-10-11 and is a handover for implementation.*

## Problem Statement

Every stage load since 2026-10-02 fails in all three Ingest activities of Fabric Pipeline
`pl_stage_load_NYC_Crashes` with `DELTA_MULTIPLE_SOURCE_ROW_MATCHING_TARGET_ROW_IN_MERGE`.

Root cause: the watermark-from-loaded-data change (archived spec, done 2026-10-02) reset all three
watermarks to 2026-06-11 and added a 7-day read lookback. The verifying **CDC run** `8552e9f4` landed
rows dated 2026-06-05 → 2026-06-11, which the 2026-09-10 full extract already holds. That overlap was
intended: the spec assumed "downstream de-duplicates the overlap". It does not. Fabric Notebook
`nb_cdc_to_delta` reads every file in a source folder as one dataset, so the same key arrives twice in
one MERGE source, which Delta rejects. MERGE only reconciles source against target, never source
against source. Every future lookback run will recreate the overlap, so this is permanent, not a
one-off.

The `.csv` extension is not a cause. Files were renamed `<runId>.csv` by the same change; the
`file_pattern = "*"` glob reads both the old extensionless files and the new ones.

Separately, landing folders `Files/raw/<source>/` are untidy: one extensionless full extract, a
`<runId>.csv` per CDC run (many header-only, landed while NYC Open Data has been frozen since
2026-06-15), mixed naming, and overlapping rows.

## Solution

1. `nb_cdc_to_delta` keeps one row per natural key, from the newest file, before the MERGE. Repeated
   keys across files, and any within one file, can no longer fail a load.
2. A one-time cleanup consolidates each landing source folder into a single de-duplicated baseline
   CSV, after backing the originals up to an archive folder. Header-only and overlapping files go.

The landing files are not re-downloaded. NYC Open Data is frozen, so a fresh full pull would return
the same rows at high cost, and the files feed Dev, Test and Prod through one shortcut (ADR-0002).

## User Stories

1. As the operator, I want a stage load to succeed when a key appears in more than one landing file, so that the watermark lookback never breaks ingestion.
2. As the operator, I want the surviving row for a repeated key to come from the newest file, so that a late correction published by NYC wins over the older copy.
3. As the operator, I want "newest" decided by file modification time, not file name, so that run-ID names (which do not sort by date) cannot pick the wrong row.
4. As the operator, I want a deterministic tie-break when two copies share a modification time, so that reruns give the same table.
5. As the operator, I want the notebook to print how many duplicate rows it dropped per source, so that each run leaves a visible record of the overlap.
6. As the operator, I want de-duplication to apply on the first-run write path as well as the MERGE path, so that a new stage never creates a table with duplicate keys.
7. As the operator, I want the de-duplicated result to give the same Delta tables as today for keys that were never duplicated, so that downstream Warehouse procedures see no change.
8. As a stage operator (Dev/Test/Prod), I want the fixed notebook promoted to every stage, so that Test and Prod do not fail on their next load.
9. As the operator, I want each landing source folder to hold one baseline file plus later CDC files, so that the folder is easy to read.
10. As the operator, I want a backup of every original landing file before anything is deleted, so that the cleanup can be reversed.
11. As the operator, I want the baseline file to be a standard header-row CSV that `nb_cdc_to_delta` reads unchanged, so that no notebook change is tied to the cleanup.
12. As the operator, I want the baseline file to keep every source column, not just the modelled ones, so that the landing zone stays raw.
13. As the operator, I want the baseline row count per source to equal the distinct key count of the originals, so that I know nothing was lost or duplicated.
14. As the operator, I want the `.keep` placeholder kept, so that the folder survives being emptied.
15. As the operator, I want the watermarks untouched by the cleanup, so that the next CDC run still queries from 2026-06-04.
16. As the operator, I want the 17 reported within-file duplicate crash keys re-checked with a `multiLine` read, so that I know whether they are real or an artefact of a split read.
17. As the operator, I want the Delta tables in each stage verified one row per key after the fix, so that any duplicates already written are caught.
18. As a future maintainer, I want notebook comments and the ingestion doc to describe the de-duplication and the baseline file, so that the "downstream de-duplicates" claim is finally true and documented.

## Implementation Decisions

- **Modules changed:** Fabric Notebook `nb_cdc_to_delta` (Dev, promoted to Test/Prod). Landing lakehouse
  `Files/raw/{crashes,persons,vehicles}` (data only, one-off). Doc `docs/socrata-ingestion.md`.
  No change to `nb_etl_watermark`, `pl_cdc_NYC_Crashes_Landing`, the Warehouse procedures or the model.
- **De-dup step location:** after the audit columns are added (Cell 5), before the write (Cell 6). Rank
  rows per natural key by file modification time descending, then source file path descending as the
  tie-break; keep rank 1. File modification time comes from Spark's file `_metadata` column; check it is
  available on the Fabric runtime, and fall back to listing file times if not.
- **Interface unchanged:** same parameters, same exit values (`SUCCESS|<source>`, `NO_NEW_DATA`), same
  target tables and columns. The ranking column is dropped before the write.
- **Cleanup runs once, over Livy against the landing lakehouse.** It is a data operation, not an item
  definition change, so it sits within "MCP is run/read/validate only". The script is recorded in the
  ticket for audit.
- **Cleanup method per source:** copy all files to `Files/archive/2026-10-11/<source>/`; read the
  originals with `header` and `multiLine`; keep the newest row per key with the same rule as the
  notebook; write one CSV with `quote`/`escape` set to `"` so embedded quotes and line breaks
  round-trip; move the single part file to `Files/raw/<source>/full_2026-10-11.csv`; delete the originals
  except `.keep`.
- **Baseline naming:** `full_<yyyy-MM-dd>.csv`. Later CDC files keep `<runId>.csv`; the watermark
  Advance step reads only its own run's file, so the baseline name does not affect it.
- **Lineage trade-off:** after the next MERGE every row's `_source_file` points at the baseline file.
  The archive folder keeps the original lineage.
- **Promotion:** deploy only the notebook Dev → Test → Prod. Do not include the Warehouse (it can wipe
  tables on deploy).

## Summary of sequence of operations

2. CC does: update notebook comments and ingestion doc; commit locally.
3. User does: push; Dev Source Control → Update All.
4. CC does: run Dev stage load against current duplicate files.
5. CC does: verify Dev Delta tables one row per key.
6. CC does: re-check within-file crash duplicates using multiLine read.
7. CC does: back up landing files to archive folder.
8. CC does: write one de-duplicated baseline CSV per source.
9. CC does: verify counts, delete originals, rerun Dev stage load.
10. User does: deploy notebook to Test, Prod; CC runs loads.

## Testing Decisions

- **Seam: one.** The highest existing seam is a run of `pl_stage_load_NYC_Crashes` per stage, checked
  through its activity outcomes and Spark reads of the resulting `nyc_*` Delta tables. No unit tests on
  notebook internals.
- **Good tests check external behaviour only:** the pipeline succeeds; each `nyc_*` table has
  `count = countDistinct(key)`; row counts move only by genuinely new keys; downstream procs complete.
- **Test 1, against real duplicates (before cleanup):** Dev stage load succeeds; key uniqueness holds;
  printed drop counts match the overlap (crashes 1,278 multiLine rows in run `8552e9f4`, persons 4,221,
  vehicles 2,470, all already in the full extract).
- **Test 2, cleanup is lossless:** per source, baseline rows = distinct keys across originals; archive
  file count = original file count; a Dev stage load after cleanup leaves `nyc_*` row counts unchanged.
- **Test 3, Test/Prod:** stage loads succeed; key uniqueness holds.
- **Prior art:** `/dax-smoke-test` skill (pre/post counts, Spark key checks); Spark reads of Warehouse
  and Lakehouse Delta by OneLake path; archived watermark-from-loaded-data ticket 04 (landed-file row
  counts read with `multiLine`).

## Out of Scope

- A fresh full re-download from Socrata, or resetting the watermarks.
- Making `nb_cdc_to_delta` read only new files (true incremental read).
- Scheduled or automatic landing-folder compaction.
- Warehouse procedure changes; `usp_load_fact_*` already insert only absent keys.
