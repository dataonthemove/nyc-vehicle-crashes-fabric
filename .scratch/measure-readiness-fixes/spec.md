# Measure-readiness fixes: date sorting, blank members, Person Age, Vehicle Model Year

Status: ready-for-agent
Category: bug
Raised: 2026-10-10 (measure-readiness review of the Dev semantic model)

> *This was generated by AI from a conversation and is the spec for ticket breakdown.*
> Evidence below comes from DAX run against the Dev semantic model on 2026-10-10 (`execute_dax_query`).

## Problem Statement

Pat wants to add a base layer of measures to `NYC_VehicleCrashes_Semantic`. A full review of the model
found it structurally sound:

- the live Dev model matches git, except for column order, which is cosmetic;
- all 15 relationships are correct, and the bridge filters in both directions;
- there are no orphaned or NULL fact keys, and every dimension key is unique;
- every bridged factor filters all three facts;
- `Dim Date` is a contiguous, marked date table;
- the occupancy cap is live.

The review also found four defects. They don't stop measures from being written, but each one would make
the first report look broken or give wrong numbers. Two are in the semantic model and two are in the
Warehouse ETL.

### Issue 1: Month and Day of Week sort alphabetically, and Date shows a time

**What it is.** In `Dim Date`, the `Month` and `Day of Week` text columns have no sort-by column. Power BI
therefore orders them alphabetically: April, August, December … and Friday, Monday, Saturday …. The
numeric partners that would fix this, `Month Number` and `Day of Week Number`, already exist in the
table. The `Date` column also has the format string `General Date`, so every date shows a midnight
timestamp.

**Why it matters.** Month and weekday are the most common axes for crash data: seasonality, and weekday
vs weekend. A trend chart in alphabetical month order is unreadable, and it is the first thing a
reviewer notices. Report authors can't fix it per visual. A sort-by column is a model property, and
without it every visual has to be re-sorted by hand, which still can't put months in calendar order.

**Evidence.** The model's column metadata (`INFO.VIEW.COLUMNS`) shows no sort-by column on `Month` or
`Day of Week`, and `FormatString = General Date` on `Date`. No `sortByColumn` appears anywhere in the
model's TMDL.

### Issue 2: Every slicer shows a "(Blank)" item, though no data is missing

**What it is.** Every dimension carries an extra blank member. This holds for all eight tables on the
one-side of a relationship: `Dim Date`, `Dim Location`, `Dim Person`, `Dim Vehicle`,
`Dim Vehicle Circumstance`, `Dim Driver`, `Dim Contributing Factor` and `dim_factor_group`. A query
with no measure returns it as an extra value. For example, Borough returns seven values: the five
boroughs, `UNKNOWN`, and a blank.

In an Import model, that blank row appears only when fact rows have keys with no matching dimension
row, which is a referential-integrity violation. Here there are none: all 15 relationships have zero
orphaned or NULL keys. Community reports, not official Microsoft documentation, say Direct Lake adds the
blank row as a safeguard whenever a relationship doesn't assume referential integrity. No relationship
in this model does: `RelyOnReferentialIntegrity = false` on all 15.

**Why it matters.**
- **Slicers show "(Blank)".** A slicer has no measure, so it lists the blank member. Every Borough,
  Month, Person Type or Vehicle Type slicer will offer "(Blank)". Report users will read it as missing
  data, and on a public portfolio it looks like a data-quality defect.
- **It hides real failures.** A real orphan from a broken load would show up as the same "(Blank)". The
  safeguard blank makes a genuine integrity failure indistinguishable from normal behaviour.
- **Slower fallback queries.** When a Direct Lake query falls back to DirectQuery, relationships that
  don't assume integrity are sent as outer joins, which cost more than inner joins.

**Evidence.**
- On all eight dimensions, `ALL(key)` returns one more row than `ALLNOBLANKROW(key)`.
- A measure-less `SUMMARIZECOLUMNS` over Borough returns seven rows. Over Month it returns 13 values,
  but only 12 once a measure is added.
- Counting fact rows mapped to the blank member returns 0 on all 15 relationships.

### Issue 3: Person Age contains impossible values and uses 0 for "unknown"

**What it is.** `Fact Crash Persons`[Person Age] (Warehouse `fact_persons.person_age`) is loaded as
`TRY_CAST(source AS INT)` with no validation.

Distribution across 5,984,110 person rows:

| Band | Rows |
|---|---|
| < 0 (min −999) | 1,323 |
| 0 | 548,420 |
| 1–17 | 278,921 |
| 18–99 | 4,475,346 |
| 100–110 | 288 |
| 111–120 | 627 |
| 121–999 | 1,496 |
| > 999 (max 9999) | 1,778 |
| blank | 675,911 |

There are two problems:

- **Out-of-range values.** Above 110 the count jumps from 76 rows (ages 106–110) to 627 (111–120): the
  tail there is junk, not a real age distribution.
- **Zero means "unknown" for most rows.** 548,420 rows are 0. Of those, 507,484 belong to Person Role
  `Registrant`, a vehicle's registered owner who was not in the crash. Another 6,890 are Drivers, who
  can't be 0 years old. Real infants appear only among Passengers (17,308 zeros) and Pedestrians (1,157
  zeros).

**Why it matters.**
- **The average is wrong.** The column's default summarisation is `Average`, so the model already offers
  a wrong average age: 37.6 on raw data, against 40.2 for ages 1–110.
- **Age bands get garbage.** Age-band analysis would show negative ages and 9,999-year-olds.
- **"Children" is inflated.** Half a million registrant zeros would count as children.
- **Fixing it in DAX would not cover everyone.** Every age measure would have to repeat the same
  filters, and Spark, SQL and implicit-measure consumers would still see the raw values. The project
  rule set by the occupancy fix is to correct data defects in the ETL, not in DAX.

### Issue 4: Vehicle Model Year contains impossible values

**What it is.** `Dim Vehicle`[Vehicle Model Year] (Warehouse `dim_vehicle.vehicle_year`) is loaded as
`TRY_CAST(source AS SMALLINT)` with no validation. Across 4,551,002 crash–vehicles:

| Band | Vehicles |
|---|---|
| < 1900 (min 1000) | 3 |
| 1900–1979 | 1,019 |
| 1980 to the crash year + 1 | 2,565,151 |
| more than a year newer than the crash, up to 2100 | 1,196 |
| > 2100 (max 20063) | 1,728 |
| blank (unreported) | 1,981,905 |

About 2,927 vehicles carry an impossible year, held on about 1,719 of the 155,594 `Dim Vehicle` rows.
The 1900–1979 band is plausible: classic and historic vehicles.

**Why it matters.**
- **Visible junk.** A Model Year slicer or axis would start at 1000 and end at 20063.
- **Broken vehicle-age measures.** Any vehicle-age measure (crash year minus model year) would produce
  negative ages and ages in the thousands.

**What makes it harder.** `dim_vehicle` is keyed on its whole attribute set: type, make, year and
registration state. The year therefore can't be patched in place. That is unlike Person Age, which is a
plain fact column.

## Solution

Fix each defect at its source, so that every consumer sees clean values. Issues 1 and 2 are semantic
model property changes. Issues 3 and 4 are Warehouse ETL changes with a one-time remediation of rows
already loaded. All four are proven in Dev, then promoted to Test and Prod through the deployment
pipeline.

1. **Sorting and date format.** Set `Month` to sort by `Month Number`, and `Day of Week` to sort by
   `Day of Week Number`. Give `Date` an ISO date format (`yyyy-mm-dd`) with no time.
2. **Blank member.** Set `relyOnReferentialIntegrity` on all 15 relationships. This is unproven, so it is
   verified in Dev first. If the blank member remains, revert the flag, because it then carries risk
   with no benefit, and record the finding.
3. **Person Age.** Load a value as NULL (unknown) when it is negative or above 110. Also load 0 as NULL,
   except where Person Role is `Passenger` or `Pedestrian`, the only roles where an infant is plausible.
   Run a one-time, idempotent backfill in each stage, because the load procedure is incremental and
   would never revisit rows already loaded.
4. **Vehicle Model Year.** Load a value as NULL unless it lies between 1900 and the crash year + 1. A
   new model year goes on sale the year before it is named, so crash year + 1 is the latest possible
   year. Apply the identical expression in the dimension load and in the fact's vehicle-key lookup.
   Rebuild `dim_vehicle` and `fact_crash_vehicle` in each stage.

## Implementation Decisions

- **Two independent commits.**
  - *Model commit (issues 1–2):* TMDL only. Lands first, because it is quick and has no data
    remediation.
  - *ETL commit (issues 3–4):* procedures, backfill and documentation.
- **Issue 1, model only.**
  - `Dim Date`[Month] sorts by [Month Number]; [Day of Week] sorts by [Day of Week Number]. Both
    mappings are 1:1, which a sort-by column requires.
  - `Dim Date`[Date] gets an ISO date format string.
  - No Warehouse change. Keep `dataCategory: Time` and `isKey` intact (the date-table marking).
- **Issue 2, model only.**
  - Set `relyOnReferentialIntegrity` on all 15 relationships, the bridge relationships included, for
    consistency.
  - **Precondition.** No NULL and no orphaned many-side keys. The ETL guarantees this by construction:
    - `fact_crashes` requires a valid crash date, resolves location through the Unknown member and the
      factor group through an inner join;
    - line facts take their header keys from `fact_crashes` by inner join;
    - every other key is resolved by inner join.
  - **Guard.** `/dax-smoke-test` check 3 (orphans) after every stage load is the standing proof. Extend
    check 6 so it also asserts `RelyOnReferentialIntegrity = true` (`INFO.VIEW.RELATIONSHIPS` exposes
    it).
  - **Accepted risk.** If an orphan ever appears, its rows drop out of dimension-filtered totals instead
    of showing as "(Blank)". Check 3 is what catches it.
  - **Go/no-go in Dev.** Go only if the blank member is gone on all eight dimensions. Otherwise revert,
    and record the result in this spec's Comments.
- **Issue 3: rule in the fact load.**
  - `etl.usp_load_fact_persons` loads `person_age` as NULL when it is < 0 or > 110. It also loads 0 as
    NULL unless the source person role is `Passenger` or `Pedestrian`.
  - Person Age is a fact column, not part of any key, so no rebuild is needed.
  - `summarizeBy: average` is unchanged.
- **Issue 3: backfill.**
  - A one-time, idempotent `UPDATE` applies the same rule to rows already loaded. It joins to
    `dim_person` for the role.
  - It lives as a run-once cell in the fact-persons transform notebook, following the occupancy
    backfill cell in the crash-vehicle notebook. Pat runs it in each stage's SQL editor.
- **Issue 4: rule and key expression.**
  - `etl.usp_load_dim_vehicle` loads `vehicle_year` as NULL unless it lies between 1900 and the crash
    year + 1. The crash year comes from the same source vehicle row's crash date.
  - `etl.usp_load_fact_crash_vehicle` uses the identical expression in its `dim_vehicle` lookup. Mark
    both with an "identical in …" comment, following the factor-set hash comment shared by three
    procedures.
- **Issue 4: rebuild, not patch.**
  - Pat empties `dim_vehicle` and `fact_crash_vehicle` in each stage. The stage load pipeline then
    reloads them: both procedures are incremental and refill empty tables.
  - In-place cleansing was rejected for three reasons:
    - a dimension row carries no crash date, so the crash-relative rule can't be applied to it;
    - a static bound goes stale as new model years arrive;
    - nulling years in place creates duplicate attribute sets, which double fact rows on the next load.
  - `vehicle_key` values are regenerated. This is accepted: the keys are hidden and used only by
    relationships.
- **Two copies, one commit.** Each changed procedure is edited in both its authoring notebook and the
  Warehouse item definition, in the ETL commit (CLAUDE.md rule).
- **Promotion.**
  - Dev → Test → Prod through `dp_NYC_VehicleCrashes`, by Pat.
  - No table schema changes, so no drop-first is needed. Row counts are still checked after each deploy
    that includes the Warehouse.
  - Each stage then gets its own backfill and vehicle rebuild.
- **Documentation.** Update the model documentation (Dim Date row, Relationships section, Person Age and
  Vehicle Model Year rules) and the markdown headers of the three affected transform notebooks.
- **Who does what.**
  - *Pat:* push, Source Control Update All, the backfill and table-emptying scripts (supplied by CC),
    and deployment-pipeline promotion.
  - *CC:* TMDL and procedure edits, commits, pre-drop counts, pipeline runs, `refresh_semantic_model`,
    DAX verification, smoke tests.

## Out of Scope

- Writing any measures, or setting `discourageImplicitMeasures`. That is the measure-layer spec, which
  follows this one.
- Standardising Vehicle Type (2,168 values) or Vehicle Make (11,308 values) free text.
- Week-start order: `day_of_week` 1 = Sunday. A Monday-first week needs a `dim_date` change.
- A calendar hierarchy or a Year-Month column.
- Line-to-header filtering (`.scratch/_Doubtful/line-to-header-filtering/`).
- The cosmetic live-vs-git column-order difference in the semantic model.
- Hiding the technical tables `bridge_crash_factor` and `dim_factor_group` at table level.
- A CDC run.

## Further Notes

- **Issue 2 rests on community reports, not Microsoft documentation.** Treat the Dev verification as
  the decision point, not a formality. Sources:
  [Fabric Community thread](https://community.fabric.microsoft.com/t5/Service/Setting-quot-assume-referential-integrity-quot-for-all-relations/m-p/4663935);
  [SQLBI on the blank row](https://www.sqlbi.com/articles/understanding-blank-row-and-limited-relationships/).
- **The zero-age rule is the one judgement call.** The simpler alternative nulls only values below 0
  and above 110, and leaves registrant zeros to be excluded by measure scope. It was rejected because
  every unscoped age measure would then be skewed by about 507k zeros.
- **Issue 4 pre-drop counts.** If a CDC run lands between capture and reload, fact counts rise
  legitimately; explain the difference rather than fail the check.
- **Inputs to the measure-layer spec, not fixed here:**
  - From 2016, 41% of person rows are Registrants (vehicle owners not in the crash). Also
    Witness/Owner/Notified Person/Policy Holder. A "persons involved" count must exclude these roles.
  - Before 2016 the persons data holds only injured or killed people, with no Person Role.
  - Reported injury counts (header) and recorded injured persons (line) differ slightly, for example
    2026 killed: 68 vs 89. `CONTEXT.md` already says neither silently replaces the other.
  - 43.5% of vehicles have no model year and 40% have no occupants, so ratio measures need coverage
    measures alongside them.
  - Data ends 2026-06-11 while `Dim Date` runs to 2030-12-31. Time-intelligence measures should anchor
    to the last loaded date, not `TODAY()`.
- **Stale glossary entry.** `CONTEXT.md` still lists *Occupancy* as an open term with "no agreed cap".
  The cap (100) has existed since 2026-08. Correct it in the documentation step.
