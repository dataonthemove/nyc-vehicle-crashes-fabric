# Warehouse fact-table column reorder (local-first)

Status: ready-for-agent
Category: enhancement
Raised: 2026-09-29 (column-ordering session)

> *This was generated by AI from a conversation and is the spec for ticket breakdown.*
> Companion change: the semantic model fact columns were already reordered in TMDL (2026-09-28).

## Problem Statement

The three Warehouse fact tables list their columns in load order: surrogate row ID first, the
degenerate `collision_id` buried among the foreign keys, and `latitude`/`longitude` ahead of the
counts in `fact_crashes`. Anyone reading the tables in the Warehouse explorer, a `SELECT *`, or the
exported table definitions sees no Kimball structure, and the Warehouse no longer matches the column
order just adopted in the semantic model.

## Solution

Reorder the columns of `fact_crashes`, `fact_persons` and `fact_crash_vehicle` to:
business key → row ID → foreign keys → facts → semi-facts → other. The change is authored
**local-first**: both repo copies of the table DDL are edited and pushed, the star tables are
dropped in each stage, the new definitions are pulled (Dev) or promoted (Test, Prod), and every
stage is fully reloaded and validated. Dimension tables already follow surrogate-key-then-attributes
and are unchanged.

Target order:

| Table | Order |
|---|---|
| `fact_crashes` | `collision_id`, `crash_id`, `date_key`, `location_key`, `factor_group_key`, 8 injured/killed counts, `latitude`, `longitude` |
| `fact_persons` | `collision_id`, `fact_person_id`, `date_key`, `location_key`, `factor_group_key`, `person_key`, `person_age`, `is_injured`, `is_killed` |
| `fact_crash_vehicle` | `collision_id`, `fact_crash_vehicle_id`, `date_key`, `location_key`, `factor_group_key`, `vehicle_key`, `vehicle_circumstance_key`, `driver_key`, `vehicle_occupants` |

## Implementation Decisions

- **Local-first route (decided 2026-09-29).** Committing the Warehouse from the Source Control pane
  is reserved for cosmetic drift; a column reorder is substantive, so both repo copies are edited
  locally and pushed.
- **Two copies, one commit.** The facts DDL notebook and the Warehouse item definition's fact table
  files change together (same rule as the load procs).
- **Scope: three fact tables only.** Dimensions, bridge and `etl_watermark` keep their definitions.
- **Drop all 12 star tables, not just the facts.** The load procs are insert-only full rebuilds and
  assume empty tables; reloading with dimensions present duplicates them.
- **No proc changes.** Every `INSERT` names its columns explicitly, so it is order-independent.
- **No semantic model changes.** Direct Lake binds by `sourceColumn`; the TMDL order is already the target.
- **IDENTITY surrogate keys are regenerated** in every stage. Accepted: keys are hidden and joined only by relationships.
- **Stage downtime accepted.** Each stage is empty from drop until its reload completes.
- **Who does what.** Pat: drops (SQL editor, script supplied by CC), Source Control Update All,
  deployment pipeline promotion. CC: file edits, commit/push, row counts, `sys.tables` check,
  DDL notebook fallback jobs, pipeline runs, smoke tests.

## Summary of sequence of operations

1. Reorder fact columns in DDL notebook and item definition.
2. Commit both copies together and push to ADO.
3. Capture Dev pre-drop row counts.
4. Drop all 12 star tables in Dev.
5. Run Update All in Dev Source Control.
6. Check Dev `sys.tables`; run DDL notebooks if missing.
7. Run stage load pipeline in Dev.
8. Smoke-test Dev against pre-drop counts.
9. Capture counts, drop star tables, promote Dev to Test.
10. Check tables, reload and smoke-test Test.
11. Capture counts, drop star tables, promote Test to Prod.
12. Check tables, reload and smoke-test Prod.

## Testing Decisions

- **One seam: the stage's star schema after reload**, observed through `/dax-smoke-test`
  (pre-drop counts, key agreement, orphans, factor-group integrity, bridge filtering, relationships).
  It tests external behaviour — the loaded data — not the DDL text.
- **Column order itself** is verified by listing each fact's columns in ordinal order from the
  Warehouse catalog via Livy/synapsesql and comparing against the target table above.
- **Pass criteria per stage:** post-reload fact counts equal pre-drop counts; smoke test all green;
  catalog order matches target; Source Control shows the Warehouse in sync (Dev).
- Prior art: `/dax-smoke-test` runs after the header/line remodel (2026-09-27) in all three stages.

## Out of Scope

- Reordering dimension or bridge tables.
- Any change to load procs, `etl_watermark`, the semantic model or reports.
- Renaming columns or introducing friendly names.
- Hiding columns or display folders (done/considered separately in the semantic model).
- A CDC run.

## Further Notes

- Deploy caveats from 2026-09-27: a promotion into live old-schema tables fails with
  `Invalid column name` and may appear as a UI hang; the deploy may also silently skip creating
  tables. Both are covered by drop-first and the `sys.tables` check.
- After the reload, run `refresh_semantic_model` again if DAX returns `Failed to resolve name` — the
  pipeline's refresh can race the reload.
- The earlier `SELECT *` validation queries in the DDL notebooks will return the new order; nothing depends on position.
