# One factor-group view instead of three pasted CTEs

## Problem

The **Factor group** identity is pasted verbatim into three procs that must agree byte for byte.
It consists of:

- a 5-way UNION unpivot of the contributing factors;
- removal of `'Unspecified'`;
- `HASHBYTES('SHA2_256', ISNULL(STRING_AGG(...), ...))`.

The three copies are in:

- `usp_load_dim_factor_group.sql` lines 6–32
- `usp_load_fact_crashes.sql` lines 18–44
- `usp_load_bridge_crash_factor.sql` lines 6–32

The unpivot alone is a fourth copy, in `usp_load_dim_contributing_factor.sql` lines 7–18. The
`'Unspecified'` rule and the empty-set hash are restated again in CC skill `dax-smoke-test`
(`EMPTY_SET_HASH`). If any copy drifts, `fact_crashes` points at groups that the bridge never
resolves.

## Proposal

Create a view `etl.v_crash_factor_set` that returns `collision_id`, the distinct factor list and
`factor_set_hash`. The three procs select from it. `usp_load_dim_contributing_factor` and the
smoke test's factor-group check (check 4) read it too.

This is also the smallest way to prove that a Warehouse **view** round-trips through local item
definition → Update All → deployment pipeline. Issue 01 depends on that.

## Acceptance criteria

- [ ] The unpivot, the `'Unspecified'` rule and the hash exist only in the view.
- [ ] After a Dev reload, `dim_factor_group`, `fact_crashes.factor_group_key` and
      `bridge_crash_factor` match their pre-drop counts.
- [ ] `/dax-smoke-test` (factor-group integrity and bridged-factor filtering) passes in Dev.
- [ ] The view deploys to Test and Prod through the deployment pipeline. Drop first and check the
      tables, per the Warehouse deploy caveats.
