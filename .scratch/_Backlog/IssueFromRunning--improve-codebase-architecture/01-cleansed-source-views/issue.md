# Cleansed source views shared by each dimension and its fact lookup

Status: needs-triage
Category: refactor
Raised: 2026-11-23 (`/improve-codebase-architecture` review, top recommendation)

> *This was generated by AI during a CC architecture review and is a handover for later work.*

## Problem

Each dimension's source cleansing is written twice: once in the dimension's load proc, and again
in its fact's lookup join, which has to reproduce that cleansing exactly.

- **Model-year rule:** `BETWEEN 1900 AND YEAR(TRY_CAST(src.crash_date AS DATE)) + 1` is in
  `usp_load_dim_vehicle.sql` (lines 21 and 32) and again in `usp_load_fact_crash_vehicle.sql`
  (line 43).
- **NULL-safe matching:** the pattern `ISNULL(tgt.x,'') = ISNULL(NULLIF(TRIM(src.x),''),'')` appears
  once in each dimension's `NOT EXISTS` and once in the fact's join. That comes to person 10
  columns × 2, vehicle 4 × 2, circumstance 4 × 2, driver 3 × 2 and location 2 × 2.
- **Fact lookups are INNER JOINs:** see `usp_load_fact_persons.sql` line 42 and
  `usp_load_fact_crash_vehicle.sql` lines 39, 48 and 55. Only `dim_location` has an Unknown
  member.

If the two copies drift, fact rows are **dropped silently**. Every relationship sets
`relyOnReferentialIntegrity`, so nothing downstream notices. Today the only thing that would
catch it is the `/dax-smoke-test` count-vs-pre-drop check.

## Proposal

Create one view per source (person, vehicle, vehicle circumstance, driver, location), e.g.
`etl.v_vehicle_clean`. The view owns trimming, NULL normalisation, cleansing rules and an
attribute hash. The dimension proc and the fact proc both read from the view. The fact proc then
joins on the single hash instead of N normalised columns, and uses a `LEFT JOIN` that falls back
to the dimension's **Unknown member**. Per CONTEXT.md, the Unknown member's key is found by
lookup and never hard-coded.

## Open questions

- Should the hash be persisted on the dimension (a new column, which is a DDL change plus a
  reload), or recomputed in the view on both sides?
- Do Unknown members for person, vehicle, circumstance and driver change any measure results?
  Under ADR-0007 that would be the Logic class and needs a release note.
- Views must go into the Warehouse item definition (`etl/Views/`) and be promoted by the
  deployment pipeline. Prove this with issue 02 first.
- Until issue 03 lands, the "two copies, one commit" rule extends to the views.

## Acceptance criteria

- [ ] Each cleansing rule exists in exactly one view.
- [ ] No fact load proc INNER JOINs to a dimension; unmatched rows land on that dimension's
      Unknown member.
- [ ] After a full Dev reload, fact row counts equal the pre-drop counts, or every difference is
      explained.
- [ ] `/dax-smoke-test` passes in Dev; Test and Prod follow the normal promotion.
