# Deploy Test/Prod through a service principal from ADO, not as a human in the UI

Status: needs-triage
Category: enhancement
Raised: 2026-11-21 (conversation: Prod workspace allows ad hoc report creation)

> *This was generated by AI during a CC session and is a handover for later work.*

## Problem

The Fabric deployment pipeline promotes content, but it doesn't lock the target workspace.
To deploy, an identity needs pipeline Admin **and** Contributor or higher on the source and
target workspaces. Anyone who can deploy to Prod workspace `4_NYC_VehicleCrashes_prod` can
therefore also create ad hoc items there. This was confirmed when Pat created a report directly
against the Prod semantic model. That bypasses ADR-0006 (reports are authored code-first and
promoted through the pipeline).

A dedicated human "service account" doesn't fix this. Someone still holds its password and can
sign in to the portal, it hits MFA and Conditional Access prompts that break unattended runs,
and its audit trail only says "the service account did it."

## Proposal

Keep the **same** Fabric deployment pipeline, but have a service principal trigger it through
the REST API (`Deploy Stage Content`) from an ADO pipeline. Make that service principal the only
Contributor+ identity on the Prod workspace. Humans drop to Viewer, with one break-glass Admin.

Elements to create:

1. **Entra admin center** (`entra.microsoft.com`): an app registration (the service principal)
   and a security group that contains it. ADO can create the app registration automatically when
   you create the service connection with workload identity federation set to *automatic*. Either
   way, you need permission to register apps in the tenant.
2. **Fabric admin portal:** the tenant setting "Service principals can use Fabric APIs", scoped
   to that security group only.
3. **Fabric:** the service principal becomes pipeline Admin and Contributor on the Test and Prod
   workspaces. Humans drop to Viewer on Prod.
4. **ADO project:** a service connection (workload identity federation, no secret), a YAML
   pipeline in the repo (e.g. `ops/deploy/`) that calls `Deploy Stage Content`, and an ADO
   Environment with an approval check that gates the Prod stage.

Trigger: run manually or on push to `main`. The approval check gates Test → Prod.

Reference: [Automate deployment pipelines by using Fabric APIs](https://learn.microsoft.com/en-us/fabric/cicd/deployment-pipelines/pipeline-automation-fabric)
(the URL was given from memory and hasn't been opened).

## Effort and blast radius

Effort is roughly half a day. The blast radius is small: every step adds something new, and UI
deployments keep working until the human roles are downgraded.

## Risks

- **Lockout:** keep one break-glass Admin on every stage workspace.
- **Unsupported item types:** not every item type supports deployment by a service principal.
  The Warehouse is a suspect. Check the current Microsoft Learn list, then run a trial
  Dev → Test deploy before downgrading anyone.
- **Ownership:** items the service principal deploys become owned by it. The semantic model's
  Direct Lake (SQL) credentials and refresh may need rework, and the stage-load pipeline's
  Refresh activity may also be affected.
- **Tenant setting scope:** enable it for the security group only, never the whole organization.
- **Trial capacity:** the workspaces sit on a rotating trial capacity (see
  `Context/capacity-reassignment-runbook.md`). Confirm the service principal's roles survive a
  capacity reassignment.

## Acceptance criteria

- [ ] An ADO pipeline deploys Dev → Test → Prod as the service principal, and an approval

- [ ] Every item type in the pipeline deploys successfully as the service principal, or the
