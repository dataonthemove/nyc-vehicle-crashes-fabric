# Spec: Stage load pipeline (Ingest → Transform → Refresh)

Status: ready-for-agent
Category: enhancement
Raised: 2026-09-21

> *This was generated by AI from a grilling session on 2026-09-21 and is a handover for implementation.*

## Problem Statement

Since the landing-zone split (ADR-0002), raw Socrata data arrives once, in the landing workspace, via
the **CDC run**. Below landing nothing is orchestrated. In each stage (Dev, Test, Prod) the operator
has to run the Ingest notebook three times, then twelve Transform procedures in the right order, then
the semantic model refresh, all by hand. A step run out of order, or skipped, leaves the star schema
half-loaded with nothing to flag it, and Prod only goes fresh when someone remembers to do it.

## Solution

One Fabric Data Pipeline per stage runs a complete **Stage load**: Ingest the three raw sources into
Delta, Transform them into the Warehouse star, then Refresh the Direct Lake semantic model. Dev and
Prod run it on a daily schedule after the CDC run has landed new files. Test runs it manually after a
deployment. If any step fails, the run stops before Refresh, so the model never frames a half-loaded
star. The failure shows in the Monitor hub's run history.

## User Stories

1. As the operator, I want one pipeline to run the whole Stage load, so that I stop sequencing sixteen manual job runs.
2. As the operator, I want the Stage load to run daily at 04:00 in Dev, so that Dev picks up the 02:00 CDC run without my involvement.
3. As the operator, I want Prod to run the same Stage load daily at 04:00, so that Prod reports are fresh every morning.
4. As the operator, I want Test to run the Stage load only when I trigger it, so that Test stays a controlled post-deployment check.
5. As the operator, I want the three Ingest sources (crashes, persons, vehicles) to run in parallel, so that the Stage load finishes sooner.
6. As the operator, I want each Ingest call to pass its own merge key, so that persons and vehicles merge on their row identifier rather than collapsing onto the crash identifier.
7. As the operator, I want Ingest to re-read every landed file on each run, so that the Delta tables are always a complete, simple merge of landing, with no stage-side watermark to maintain.
8. As the operator, I want an Ingest run that finds no rows to count as success, not failure, so that a quiet day does not break the Stage load.
9. As the operator, I want every Transform dimension that doesn't depend on another dimension to load in parallel once Ingest has finished, so that the Transform phase is as short as the dependencies allow.
10. As the operator, I want the factor group dimension to load only after the collision dimension, so that each crash gets its factor group.
11. As the operator, I want the three facts and the bridge to load only after every dimension they reference, so that no fact row is dropped for lack of a surrogate key.
12. As the operator, I want facts and the bridge to load in parallel with each other, so that the last Transform phase is short.
13. As the operator, I want Refresh to run only when every Ingest and Transform step succeeded, so that Direct Lake never frames a partial star.
14. As the operator, I want Refresh to use the existing refresh notebook and the Variable Library, so that each stage refreshes its own model and no literals are duplicated.
15. As the operator, I want any failed step to fail the whole pipeline run, so that the Monitor hub shows the Stage load as failed rather than succeeded with warnings.
16. As the operator, I want the failing activity to be identifiable from the Monitor hub's run history, so that I know which phase to rerun or fix.
17. As the operator, I want rerunning a failed Stage load from the start to be safe, so that recovery never needs manual cleanup.
18. As the operator, I want the pipeline definition authored locally and deployed through Git, so that it follows the same SDLC as every other artifact.
19. As the operator, I want the pipeline promoted Dev → Test → Prod by the deployment pipeline, so that all three stages run the same Stage load.
20. As the operator, I want the Stage load to call Transform procedures directly rather than their authoring notebooks, so that a run never re-executes `CREATE PROCEDURE` or DDL.
21. As the operator, I want DDL kept out of the Stage load, so that a scheduled run can never drop Warehouse tables.
22. As a report consumer, I want the model refreshed after each daily load, so that the numbers I see include yesterday's crashes.
23. As a reviewer, I want the pipeline's activity graph readable in the Git diff, so that ordering changes are reviewed in a PR.
24. As a future maintainer, I want the Stage load named in the glossary, so that "Stage load" and "CDC run" are not confused.

## Implementation Decisions

- **New item:** one Fabric Data Pipeline, `pl_stage_load_NYC_Crashes`, in the Dev workspace, Git-managed alongside the other Dev items in its own new orchestration folder. It is promoted to Test and Prod by the existing deployment pipeline.
- **No pipeline parameters and no watermark read.** The Stage load has no inputs. The landing watermark stays the CDC run's concern.
- **Ingest phase:** three parallel Notebook activities calling the existing parameterised Ingest notebook, one per source. Each passes `source_name`, `file_subfolder` and `natural_key`: crashes → `collision_id`, persons → `unique_id`, vehicles → `unique_id`. `file_pattern` keeps its default. The notebook's `NO_NEW_DATA` exit is a success exit.
- **Transform phase:** Fabric Stored Procedure activities that run the existing Transform procedures. The authoring notebooks are not called. Dependency graph:
  - Wave 1, after all Ingest succeeds: date, collision, location, contributing factor, vehicle, damage and person dimensions, in parallel.
  - Wave 2, after collision: factor group dimension.
  - Wave 3, after every dimension each one references: fact_crashes, fact_persons, fact_crash_vehicle and bridge_crash_factor, in parallel. The bridge waits for factor group and contributing factor.
  - Implementation may collapse Wave 1 into a single barrier if Fabric's dependency editor times out (known `add_activity_dependency` limitation). Correctness only needs each activity's upstream set to be a superset of its true dependencies.
- **Refresh phase:** one Notebook activity calling the existing refresh notebook, dependent on success of every Wave 3 activity. The notebook already raises on a non-`Completed` refresh, so a failed refresh fails the run.
- **Dependency condition:** every edge is *Succeeded*. There are no *On failure* or *On completion* branches. A failure stops downstream activities and marks the run failed.
- **Schedules:** Dev daily at 04:00; Prod daily at 04:00, set after first promotion (schedules are not deployed); Test none. Landing's CDC run is assumed at 02:00 but currently has no schedule. Setting one is a separate step.
- **Alerting:** none. Failures are observed in the Monitor hub. Outlook email was dropped because the Fabric trial account's ability to send is unverified.
- **Behaviour carried unchanged:** Transform procedures stay insert-only (`NOT EXISTS`); the date dimension truncates and reloads. Rerun safety relies on this.
- **Authoring path:** pipeline JSON authored locally → commit/push → Fabric Source Control Update. No MCP authoring of the definition (CLAUDE.md SDLC rule 1).
- **Glossary:** "Stage load" is added to `CONTEXT.md`.

## Testing Decisions

- **One seam: the pipeline run.** Trigger the Stage load in Dev via MCP (`run_on_demand_job`) and assert only on externally visible outcomes. Activity internals are not tested.
- **Test 1, cold-to-warm run:** the run status is Succeeded. Every activity succeeded, and Refresh ran last. Delta row counts for the three `nyc_*` tables match a Spark count of distinct merge keys in the landed files. Warehouse fact and bridge row counts are non-zero and have no duplicate business keys. Then the `/dax-smoke-test` checks pass.
- **Test 2, idempotency:** a second run with no new landed files succeeds, and every Delta and Warehouse row count is unchanged.
- **Test 3, failure gate (manual, once):** force a Transform activity to fail, e.g. by temporarily renaming its procedure in a throwaway branch workspace. Assert that Refresh did not run and the pipeline run is Failed.
- **Test 4, stage isolation:** after promotion, a manual Test run refreshes the Test model, not the Dev model. Verify with the model's last-refresh time per workspace. This guards the ADR-0003 active-value-set trap.
- **Prior art:** skill `/dax-smoke-test` for model checks; the memory note "verify Warehouse tables via Spark" for real Warehouse row counts from Livy; `get_pipeline_activity_runs` for per-activity status.

## Out of Scope

- DDL execution, and any `full_rebuild` toggle. Tracked separately in `.scratch/full-rebuild-toggle/`.
- Propagating source-row updates into the Warehouse, i.e. MERGE instead of insert-only. Tracked in `.scratch/source-row-updates/`.
- Incremental Ingest (reading only new landed files). Rejected for simplicity; every run re-reads all files.
- Email, Teams or Activator alerting.
- Triggering the Stage load from the CDC run, or event-based triggers.
- Scheduling the landing CDC run itself.
- Fixing the watermark defect (advances to run time, not max `crash_date`).
- The header/line conformed-keys issue and its RLS leak.

## Further Notes

- **Resolved (ticket 06, 2026-09-23): Stored Procedure activity binding across deployment.** Deployment rehydrates the connection's `artifactId` and `workspaceId` but leaves `endpoint` (the TDS host) as a Dev literal. Deployment Rules don't cover pipelines, and an `ItemReference` variable exposes no host. So `endpoint` is `@pipeline().libraryVariables.vl_NYC_Crashes_warehouse_endpoint`, a String variable with per-stage overrides (ADR-0003).
- **Correction: schedules are deployed.** Fabric serializes a pipeline schedule into `.schedules` in Git, and deployment copies it. The Schedules decision above assumed otherwise. Scheduling is deferred (Pat, 2026-09-23), and no stage has a schedule.
- **Cost:** Ingest re-reads about 2.9 GB of unsplittable multi-line CSV per run, and the landed file set only grows. Revisit incremental Ingest if run time becomes a problem.
- **Active value set:** each promoted stage must have `vl_NYC_Crashes` set to its own value set before the first scheduled run (ADR-0003). Otherwise Refresh silently refreshes Dev.
- **Parameter cell:** the Ingest notebook's parameter cell must be tagged, or pipeline parameters are ignored. It was already tagged in Git at time of writing.
