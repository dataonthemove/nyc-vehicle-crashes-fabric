# Crash-point coordinate cleanse for map visuals

Status: ready-for-agent
Category: bug
Raised: 2026-09-29 (map-visual coordinate check session)

> *This was generated by AI from a conversation and is the spec for ticket breakdown.*

## Problem Statement

`Fact Crashes`[Latitude] and [Longitude] are set up correctly for maps (double, `dataCategory`
Latitude/Longitude, SummarizeBy None). The values are not clean. A Spark profile of Dev
`fact_crashes` on 2026-09-29 found 2,269,187 rows:

| Class | Rows | Map effect |
|---|---|---|
| Inside the NYC bounding box | 2,020,640 | Correct |
| NULL (both coordinates) | 240,806 | Dropped by the visual, which is fine |
| Exactly (0, 0) | 7,591 | Plotted in the Gulf of Guinea; zooms the map out to fit |
| Non-zero, outside NYC | 150 | Plotted in the wrong place (lat 30.8–43.3, lon down to −201.4, which is not a real longitude) |

None of the rows have swapped coordinates, and none have only one coordinate missing.
`etl.usp_load_fact_crashes` copies the source crash point in with `TRY_CAST` and doesn't validate
it. Any map visual over `Fact Crashes` therefore opens zoomed out to the Atlantic, with about 7.7K
stray points.

## Solution

Treat a crash point outside NYC as unknown. `etl.usp_load_fact_crashes` ends with one idempotent
`UPDATE` that sets `latitude` and `longitude` to NULL on any `fact_crashes` row where either one is
outside the NYC bounding box. Because the load is incremental, a single statement fixes both the
rows already loaded and every future batch. No table is dropped. The work is built and validated in
Dev only. Test and Prod aren't promoted, loaded or validated as part of this spec. The spec only
requires that the change sits in the Warehouse item definition, so a later Dev → Test → Prod
promotion carries it, and each stage's next Stage load cleanses its own rows.

## User Stories

2. As a report author, I want no points plotted off the coast of Africa, so that the map looks credible in a portfolio demo.
3. As a report author, I want out-of-city points removed, so that a dot in New Jersey or Pennsylvania doesn't suggest a crash happened there.

7. As Pat, I want one rule in one place, so that existing and future rows are cleansed the same way.
8. As Pat, I want the cleanse to be idempotent, so that rerunning the Stage load is always safe.
9. As Pat, I want existing bad rows fixed without dropping star tables, so that a reload isn't needed in any stage.
10. As Pat, I want the raw Lakehouse `nyc_crashes` values left untouched, so that the source stays auditable.
11. As Pat, I want both repo copies of the proc changed in one commit, so that the notebook and the promoted item definition don't diverge.

## Implementation Decisions

- **Module changed:** `etl.usp_load_fact_crashes` only. Its interface doesn't change (no parameters, same pipeline activity).
- **Rule:** a crash point is valid only if latitude is between 40.49 and 40.92 **and** longitude is between −74.27 and −73.68. Otherwise both columns become NULL. This covers (0, 0), bad values like −201.4, and out-of-city points in one predicate. The box encloses all five boroughs (Staten Island south tip ≈ 40.496, Bronx north ≈ 40.915).
- **Placement:** a trailing `UPDATE dbo.fact_crashes SET latitude = NULL, longitude = NULL WHERE latitude IS NOT NULL AND NOT (<in-box>)`, after the incremental `INSERT`. It's idempotent: rows that already have NULL coordinates don't match. The INSERT keeps copying the values as-is, so the rule lives in one place.
- **Both coordinates are NULLed together**, which keeps the existing "no row has only one coordinate" invariant.
- **Bounds as `DECLARE`d variables** at the top of the proc, next to the existing Unknown-member lookup.
- **Two repo copies, one commit:** the authoring notebook `10_ETL_fact_crashes` and the Warehouse item definition's copy of the proc (CLAUDE.md rule). Match Fabric's notebook formatting to avoid round-trip diffs.
- **No schema, DDL, semantic model or TMDL change.** The existing `dataCategory`/SummarizeBy settings stay as they are. Direct Lake picks up the new values after the pipeline's Refresh activity.
- **Domain vocabulary:** "crash point" = the fact-level latitude/longitude pair (ADR-0005, D8).

## Summary of sequence of operations

1. Capture Dev baseline coordinate profile and fact counts via Spark.
2. Add bounds variables and trailing UPDATE to notebook proc.
3. Mirror identical change into Warehouse item definition proc.
4. Commit both copies together; push to ADO.
5. Source Control Update All in Dev; confirm proc altered.
6. Run Dev Stage load pipeline; refresh semantic model if needed.
7. Profile Dev: zero (0,0), zero outside-box; counts unchanged.
8. Run `/dax-smoke-test` on Dev.
9. Rerun proc in Dev; confirm profile unchanged (idempotent).
10. Close issue; note outcome in Comments.

## Testing Decisions

- **One seam: Dev's loaded `fact_crashes` after a Stage load run.** It is observed through a
  Spark profile of the Warehouse Delta table by OneLake path (the same query as the 2026-09-29
  profile), plus `/dax-smoke-test`. This tests the loaded data, not the proc text.
- **Pass criteria (Dev):**
  - (0, 0) count = 0.
  - Non-NULL rows outside the box = 0.
  - Inside-box count unchanged from baseline.
  - NULL count = baseline NULL + baseline (0, 0) + baseline outside-box.
  - Total fact row count unchanged (apart from any genuinely new collisions from the load's incremental batch).
  - Rows with only one coordinate NULL = 0.
  - `/dax-smoke-test` all green.
- **Idempotency check:** run the proc a second time. The profile must be identical.
- **Propagation check (repo only):** the notebook copy and the Warehouse item definition copy of the proc are identical after the commit. No Test or Prod run is required.
- **Prior art:** the 2026-09-29 Spark coordinate profile, `/dax-smoke-test` runs after the header/line remodel (2026-09-27), and the pre/post count discipline in `warehouse-fact-column-reorder`.

## Out of Scope

- Fixing the raw Lakehouse `nyc_crashes` table or the ingest notebook.
- Geocoding or recovering locations for NULL crash points (for example from borough/ZIP or street names).
- A precise NYC polygon test. A bounding box is enough to frame the map, and a few points in New Jersey or Nassau inside the box may remain.
- A "has valid location" flag or measure. The model has no measures (D10).
- Report/map visual authoring (Fabric web UI, separate work).
- Reordering fact columns (see `warehouse-fact-column-reorder`).
- Promoting to, loading or validating Test and Prod.

## Further Notes

- The table-drop step from earlier specs is deliberately avoided.
- For whenever Pat next promotes: a Warehouse deploy may create or wipe tables (Test was wiped 2026-09-28). Checking row counts after that promotion is recommended, but it isn't part of this spec.
- Test and Prod keep their bad coordinates until the promoted proc runs in their next Stage load.
- If `warehouse-fact-column-reorder` runs first and fully reloads the stages, the trailing UPDATE still applies unchanged on that reload.
