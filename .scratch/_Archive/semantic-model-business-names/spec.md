# Semantic model business-friendly names

Status: done
Category: enhancement
Raised: 2026-09-29 (semantic-model naming session)

> *This was generated by AI from a conversation and is the spec for ticket breakdown.*

## Problem Statement

The Direct Lake semantic model `NYC_VehicleCrashes_Semantic` shows report authors the Warehouse's
technical names unchanged. The 12 tables and 78 columns come through as `fact_crashes`,
`dim_contributing_factor`, `bridge_crash_factor`, `factor_desc`, `month_name` and so on. A business
user building a report in the Fabric web UI sees snake_case, `dim_`/`fact_` prefixes and
abbreviations in the field list rather than the terms they'd use. The model reads like a database
schema, not an analytical product, which weakens it as a portfolio piece.

## Solution

Rename the model's visible tables and columns to business-friendly names at the semantic layer only.
The Warehouse is untouched, so no table reloads are needed in any stage. Claude inventories every
name and writes a current → proposed review file, Pat approves it, then Claude edits the TMDL
locally under the normal code-first workflow. Pat deploys to Dev, a lightweight check proves the
model binds and queries, and Pat promotes to Test and Prod. The only existing report is deleted
first, so no visual rebinding is needed.

## Implementation Decisions

- **Scope is the semantic layer only.** Warehouse tables, columns, stored procedures, notebooks and
  pipelines are not changed. Only the `definition/` TMDL tree and the docs/skills that quote model
  names change.
- **Binding is preserved by leaving source references alone.** Each column keeps its
  `sourceColumn`; each table's partition keeps its `entityName`. Only object names change. Because
  the physical data is unchanged, each stage needs a metadata reframe (`refresh_semantic_model`),
  not a reload.
- **Identity is preserved.** `lineageTag` values stay unchanged on every table and column.
- **Hidden columns keep technical names by default.** All hidden columns (keys, IDs such as
  `bridge_id`) keep their current names. They're invisible to report authors, and leaving them
  keeps relationship edits small. Pat can override this per row in the review file.
- **Naming rules (proposed defaults, confirmed in the review file):** Title Case with spaces; Title Case `Dim ` / `Fact ` table prefixes
  replacing snake_case `dim_`/`fact_`; abbreviations expanded; dimensions as singular nouns; facts
  named after the business process. How the bridge table is named is decided in the review file.
- **Review artifact.** A markdown table in this feature folder: table, current name, proposed name,
  visible/hidden, notes. Pat edits it in place. Nothing in `definition/` changes until it's approved.
- **TMDL edits per renamed table:** the table declaration, the matching `ref table` line in the
  model file, the partition name (renamed to match the table, as Fabric does), the table file name,
  and every relationship `fromColumn`/`toColumn` that references the table. Names with spaces use
  TMDL single-quote syntax.
- **Relationship identifiers stay as they are.** Relationship object names are internal, so they
  keep their current snake_case names to keep the diff minimal. No `///` descriptions are added to
  relationships (known Git-import parse failure).
- **No measures, sort-by columns or hierarchies exist**, so there are no further references to
  rewrite.
- **Report removal.** Pat deletes the one existing report in the Fabric web UI and commits the
  deletion through Source Control, in every stage where it exists, before the rename deploys.
- **Doc and skill updates ship in the same commit as the TMDL rename:** the `dax-smoke-test` skill
  (its DAX references only; its Spark checks read Warehouse names, which don't change), the
  `tmdl-model-edit` skill, the CLAUDE.md SummarizeBy section, and a business-name ↔ Warehouse-name
  mapping in `CONTEXT.md`.
- **Out-of-band concerns unaffected:** Deployment Rules bind the data source, not tables (ADR-0004).
  Autobind matches the model item by its name, which doesn't change.

## Summary of sequence of operations

1. Delete the existing report in each stage.
2. Inventory all tables, columns and relationship references.
3. Write the current → proposed review file with naming rules.
4. Pat approves or amends the review file.
5. Rename tables, visible columns, partitions and files in TMDL.
6. Update relationship column references to the new table names.
7. Update the smoke-test skill, tmdl skill, CLAUDE.md and CONTEXT.md.
8. Commit, push, then Update All in Dev.
9. Refresh the Dev model; run the per-table row query.
10. Promote to Test and Prod; refresh and query each.

## Testing Decisions

- **One seam: the deployed model, queried by DAX after refresh.** Good tests exercise only external
  behavior, meaning what a report author would see. They don't inspect TMDL text.
- **Check 1: Git import.** Source Control Update All completes without `Workload_FailedToParseFile`.
  That proves every relationship and `ref table` reference resolves.
- **Check 2: framing.** `refresh_semantic_model` succeeds in the stage.
- **Check 3: binding.** One DAX query per stage returns a few rows from every table, addressed by
  its new name and selecting every renamed visible column. A column with a mistyped or altered
  source binding errors or comes back blank here.
- **Not tested:** row counts, key integrity, factor filtering. The data is unchanged, so the full
  `/dax-smoke-test` is deliberately skipped.
- **Prior art:** the DAX query patterns in the `dax-smoke-test` skill; the Direct Lake framing
  note, which says a post-deploy "Failed to resolve name" means refresh first before assuming
  breakage.

## Out of Scope

- Renaming Warehouse tables or columns, or reloading any table.
- Renaming hidden key/ID columns (unless Pat overrides this per row in the review).
- Renaming the semantic model item or any other Fabric item.
- Adding measures, display folders, hierarchies or sort-by columns.
- Rebinding or rebuilding reports; the only report is deleted.
- Running the full `/dax-smoke-test`.
- Changing relationship object names or cross-filter behavior.
