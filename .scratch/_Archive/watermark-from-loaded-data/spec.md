# Spec: Watermark from loaded data

Status: done (2026-10-02)
Category: bug
Raised: 2026-10-01

> *This was generated by AI from a working session on 2026-10-01 and is a handover for implementation.*

## Problem Statement

Each **CDC run** advances the **Watermark** to the time the pipeline ran (`utcnow()`), not to the
newest data it actually loaded. The Socrata filter is `crash_date > watermark`, so any crash published
after its own date has passed is skipped permanently.

This is no longer hypothetical. NYC Open Data has frozen all three datasets (crashes, persons,
vehicles) since 2026-06-15. A notice on each dataset says the automated update is being fixed, with a
target of August, and it is still up on 2026-10-01. The newest `crash_date` at source is 2026-06-11.
The watermarks were advanced to 2026-09-10. When NYC resumes and backfills, every crash dated
2026-06-12 → 2026-09-10 will be skipped. CDC runs since 9/10 have landed header-only files, which hides
the problem rather than revealing it.

A second gap: `crash_date` is always midnight, so even a correct watermark with a strict `>` misses
any same-day crash published later.

## Solution

The watermark records the newest `crash_date` actually landed for each source. A run that lands
nothing leaves the watermark unchanged. The watermark never moves backwards automatically. Each read
applies a 7-day lookback, so the Socrata query starts a week before the watermark and picks up
late-published rows; downstream de-duplicates the overlap. A one-time reset sets all three watermarks
to 2026-06-11, so the backfill is captured when NYC resumes.

## User Stories

1. As the operator, I want the watermark to equal the newest `crash_date` landed, so that no
   published crash is skipped because of when the pipeline ran.
2. As the operator, I want a run that lands only a header to leave the watermark unchanged, so that
   empty runs during a source outage never push the watermark past unloaded data.
3. As the operator, I want the watermark never to move backwards on its own, so that landing an older
   file cannot cause a large re-pull.
4. As the operator, I want each source (crashes, persons, vehicles) to keep its own watermark, so
   that persons and vehicles published later than their crash are still caught.
5. As the operator, I want each CDC run's query to start 7 days before the watermark, so that crashes
   published a few days late, including same-day ones, are captured.
6. As the operator, I want the stored watermark to stay the true newest-loaded date, with the
   lookback applied only when reading, so that `etl_watermark` stays honest and auditable.
7. As the operator, I want each CDC run's landed file to have a predictable name tied to that run, so
   that the Advance step reads exactly the file that run wrote and no other.
8. As the operator, I want to keep setting a watermark to an explicit value by hand, so that I can
   reset it (e.g. to 2026-06-11) or recover from a mistake.
9. As the operator, I want a manual explicit value to be allowed to move a watermark backwards, so
   that a reset is possible.
10. As the operator, I want the Advance step to fail loudly when given neither a file nor an explicit
    value, so that a misconfigured activity never writes a blank or stale watermark.
11. As the operator, I want `last_run_utc` updated on every Advance, even when the watermark is
    unchanged, so that I can see when each source was last checked.
12. As the operator, I want every notebook run to print the watermarks afterwards, as today, so that
    each run leaves a visible record.
13. As the operator, I want all three watermarks reset to 2026-06-11 before the next full CDC run, so
    that the June–September backfill is not lost.
14. As a stage operator (Dev/Test/Prod), I want the overlapping re-pulled rows to have no effect on my
    tables, so that the lookback never creates duplicate facts.
15. As the operator, I want the pipeline's description to state accurately how the watermark is read,
    so that the item metadata is not misleading.
16. As a future maintainer, I want the notebook comments to explain the file-driven advance, the
    no-regress rule and the lookback, so that the logic stays understandable to a non-Python reader.

## Implementation Decisions

- **Modules changed:** Fabric Notebook `nb_etl_watermark` and Fabric Pipeline
  `pl_cdc_NYC_Crashes_Landing`, both in the landing workspace. No downstream item changes.
- **Advance mode gets a file-driven path.** New notebook parameter `loaded_file`: the landed file's
  path, relative to the landing lakehouse `Files/`. When set, the notebook reads that one file, takes
  the newest `crash_date`, and sets the watermark to the later of the current value and that date. A
  file with no data rows leaves `last_loaded_value` unchanged but still stamps `last_run_utc`.
- **Explicit path kept as a manual override.** `new_value` still sets the watermark exactly and may
  move it backwards. It is for manual runs only; the pipeline no longer passes it. If both are set,
  `loaded_file` is used. If neither is set, the run fails.
- **Lookback is applied in read mode, not in the pipeline.** New notebook parameter `lookback_days`
  (default 7). Read mode returns each watermark minus the lookback, in the same JSON shape and
  `yyyy-MM-ddTHH:mm:ss` format as today, so the three Copy query expressions stay unchanged. The table
  stores the unadjusted value. A seed watermark (1900-01-01) passes through without the subtraction.
- **Deterministic file names.** Each `Copy_*_CDC` sink writes a file named from the pipeline run ID,
  with a `.csv` extension, into its existing `raw/<source>` folder. Each `Advance_Watermark_*`
  activity passes that same path as `loaded_file`. `nb_cdc_to_delta` reads `*` in each folder, so the
  new names need no downstream change.
- **`crash_date` parsing:** Socrata emits a floating timestamp (e.g. `2026-06-11T00:00:00.000`). It
  is parsed to TIMESTAMP and compared as a timestamp, never as a string.
- **No schema change** to `etl_watermark`. Legacy Warehouse `dbo.etl_watermark` is not touched.
- **Overlap safety is confirmed.** `nb_cdc_to_delta` MERGEs on the natural key (`collision_id` /
  `unique_id`), and the `usp_load_fact_*` procedures insert only keys not already present. Re-pulled
  rows therefore add nothing.
- **Pipeline description:** the `.platform` description says the watermark is read from the
  lakehouse SQL endpoint. Correct it to say it is read and advanced by `nb_etl_watermark`. This is
  item metadata and is git-managed.
- **Workflow:** local edits, commit, Pat pushes, then landing Source Control → Update All. Before
  starting, reactivate or discard the activities deactivated during testing on 2026-10-01, so they are
  never committed.

## Testing Decisions

- **A good test** checks external behaviour only: the `etl_watermark` row values and the read-mode
  JSON after a given call. It never checks how the notebook computes them.
- **Seam 1: `nb_etl_watermark` run on its own** (MCP on-demand job with parameters, or the Fabric UI),
  against files already in landing `Files/raw/`. Use the crashes source:
  1. Explicit `new_value = 2026-06-01` → watermark is 2026-06-01 (override path).
  2. Advance with the 9/10 full-history crashes file → watermark is 2026-06-11 (moves forward).
  3. Advance with a header-only crashes file → still 2026-06-11; `last_run_utc` changed.
  4. Explicit `new_value = 2026-07-01`, then advance with the full-history file → still 2026-07-01
     (no regression).
  5. Read mode → crashes value is 2026-06-24 (07-01 minus 7 days); table still holds 07-01.
  6. Advance with neither parameter → the run fails.
  7. Finish with the explicit reset of all three sources to 2026-06-11.
- **Seam 2: one end-to-end CDC run** after the reset. The Copy queries resolve to
  `crash_date > '2026-06-04T00:00:00'`, so even with the source frozen, three run-ID-named files land
  holding the re-pulled 06-05 → 06-11 rows, and the watermarks stay at 2026-06-11. Check the Copy step's input in the run
  output, and read files and table over Livy.
- **Prior art:** `/livy-notebook-ops` (reading `Tables/` and `Files/` from Livy), and `/dax-smoke-test`
  for the before/after-counts style of verification.

## Out of Scope

- **Source corrections:** the transform procedures never propagate updated source rows
  (`.scratch/_Doubtful/source-rows-append-only-NotUpdate`). The lookback re-lands corrected rows, but
  the Warehouse ignores them.
- **Late person/vehicle rows:** line facts skip persons and vehicles added after their crash first
  loaded (`.scratch/_Backlog/late-arriving-line-rows`). The lookback re-lands those rows, but the
  crash-grain guard still drops them.
- **Row-count audit:** recording rows landed per run, e.g. a column in `etl_watermark`. Copy output
  reports only bytes and files for these file-sink copies.
- Cleaning up the header-only files already in `Files/raw/*`; they are harmless.
- Scheduling: all runs stay manual.
